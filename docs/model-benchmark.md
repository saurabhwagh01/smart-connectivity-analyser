

# Connectivity Prediction Model Benchmark



## 1. Purpose



This document describes the benchmarking approach introduced to evaluate the network connectivity prediction models used in Smart Connectivity Analyser.



The purpose of this work is to determine whether the existing prediction model provides meaningful improvements over simpler baseline approaches and to investigate alternative models and temporal feature engineering.



Previously, the application used a HistGradientBoostingRegressor for connectivity score prediction. However, without a consistent evaluation against baseline models on held-out historical data, it was difficult to determine whether the existing model was actually providing better predictions.



The benchmark provides a reproducible evaluation process using historical network measurements.



## 2. Why These Files Were Introduced



The implementation is divided into separate files to keep benchmarking, model configuration, production prediction and testing responsibilities organized.



### backend/model_benchmark.py



This is the main benchmarking module.



It was introduced because the existing production predictor trains a model for application use but does not independently establish its predictive performance on a chronological held-out dataset.



The benchmark:



- Loads historical network measurements from the SQLite database.

- Generates supervised next-record prediction samples.

- Creates chronological training and testing partitions.

- Evaluates baseline and machine-learning models.

- Calculates MAE, RMSE and R².

- Investigates temporal feature engineering.

- Performs time-series-based hyperparameter tuning when sufficient training data is available.

- Saves aggregate evaluation results in JSON format.



It does not modify the database or replace the production prediction model.



### backend/model_config.py



This file centralizes the production model configuration and shared prediction constraints.



It was introduced to avoid maintaining separate copies of the production model parameters in the application and benchmark.



It provides:



- The production HistGradientBoostingRegressor configuration.

- A shared model-construction function.

- Measurement validation rules.

- Connectivity prediction constraints between 0 and 100.



This ensures that the benchmark evaluates the same model configuration used by the production predictor.



### tests/test_model_benchmark.py



This file contains automated tests for the benchmarking implementation.



It was introduced to verify that the evaluation process behaves consistently and that important methodological assumptions are maintained.



The tests cover:



- Database record validation.

- Deterministic record ordering.

- Sequence generation.

- Temporal feature engineering.

- Chronological train/test splitting.

- Regression metric calculations.

- Negative and undefined R² handling.

- Insufficient-data handling.

- Time-series cross-validation.

- Consistent test samples across models.

- Production configuration consistency.

- Prediction bounds.

- Database integrity.



### backend/model_benchmark_results.json



This file stores the aggregate results generated by the benchmark.



It provides a machine-readable record of the evaluation protocol, dataset size, model metrics, tuning status and data-sufficiency warnings.



The results can be regenerated using the benchmark command rather than manually editing the JSON file.



## 3. Benchmark Methodology



### Dataset



The benchmark reads historical records from the `network_tests` table in the local SQLite database.



The input features are:



- Download speed (`download_mbps`)

- Upload speed (`upload_mbps`)

- Ping (`ping_ms`)

- Jitter (`jitter_ms`)

- Packet loss (`packet_loss`)

- Connectivity score (`connectivity_score`)



Incomplete, non-numeric, non-finite and out-of-range measurements are excluded rather than imputed.



Records are ordered by timestamp, with the SQLite record ID used as a deterministic tie-breaker.



### Prediction task



The benchmark predicts the connectivity score of the next record using the immediately preceding eight complete observations.



The evaluation uses rolling one-step-ahead inputs. Earlier observed records in the test period may therefore be used as historical inputs for subsequent predictions.



### Training and testing



The default test fraction is 20%.



The split is chronological rather than randomly shuffled. This keeps later target records out of the training partition.



All candidate models and baselines are evaluated against the same held-out test targets.



### Models evaluated



The benchmark includes:



1. Previous-value baseline.

2. Training-mean baseline.

3. Linear Regression.

4. Random Forest Regressor.

5. Existing production HistGradientBoostingRegressor.

6. HistGradientBoostingRegressor with engineered temporal features.

7. An optional tuned HistGradientBoostingRegressor when sufficient training samples are available.



### Feature engineering



The engineered model uses historical temporal information, including:



- Most recent measurements.

- Historical means and standard deviations.

- Changes across the observation window.

- Short-window summaries.

- Connectivity score changes.



All engineered features for a target record are calculated using preceding records only.



### Hyperparameter tuning



Hyperparameter tuning uses expanding time-series cross-validation on training samples only.



Tuning is skipped when fewer than 30 training samples are available.



The final test partition is not used for selecting hyperparameters.



## 4. Evaluation Metrics



The benchmark reports three regression metrics.



- **Mean Absolute Error (MAE):** Measures the average absolute difference between actual and predicted connectivity scores.

- **Root Mean Squared Error (RMSE):** Measures prediction error while penalizing larger errors more strongly.

- **R² score:** Measures performance relative to a mean-prediction reference.



Lower MAE and RMSE indicate better predictions.



R² can be negative when a model performs worse than the mean-prediction reference. MAE and RMSE, in contrast, cannot be negative.



R² is reported as undefined when the test set contains fewer than two observations or has a constant target value.



Predictions are constrained to the application's connectivity score range of 0–100.



## 5. Reproducing the Benchmark



Run the benchmark from the repository root.



Default command:



```bash

python backend/model_benchmark.py

```



Specify a database:



```bash

python backend/model_benchmark.py --database ./network_history.db

```



Specify an output file:



```bash

python backend/model_benchmark.py --database ./network_history.db --output ./backend/model_benchmark_results.json

```



Change the chronological test fraction:



```bash

python backend/model_benchmark.py --database ./network_history.db --test-ratio 0.20

```



The benchmark reads the database and writes aggregate results. It does not modify historical database records or production model files.

The previous-value baseline achieved the lowest RMSE on this particular test split.



The existing production HistGradientBoosting configuration did not demonstrate an improvement over the training-mean baseline on this dataset.



These results are preliminary and should not be interpreted as evidence that one model is universally superior.



## 7. Limitations and Observations



The local database contained only 22 complete observations during this evaluation.



After sequence generation and chronological splitting, only nine training samples and five test samples were available.



This is insufficient for a reliable model-selection conclusion.



Hyperparameter tuning was therefore skipped because the training sample count was below the configured minimum of 30.



The benchmark currently focuses on classical regression models. Transformer and Temporal Convolutional Network evaluation is not included because the available dataset is too small for a meaningful comparison.



Additional real network observations should be collected before making production model-selection decisions.



The rolling one-step-ahead protocol also assumes that actual measurements become available between successive predictions. It does not represent a multi-step forecast made without new observations.



## 8. Conclusion and Recommendation



The benchmark establishes a consistent evaluation process for the existing connectivity prediction model and alternative approaches.



The preliminary results show that the previous-value baseline performed best on the currently available local test split. However, the limited dataset prevents a reliable conclusion about general predictive performance.



The recommended approach is to:



1. Retain the existing production prediction implementation while collecting more historical observations.

2. Continue evaluating candidate models against the same chronological test protocol.

3. Revisit feature engineering and hyperparameter tuning when sufficient training data becomes available.

4. Avoid replacing the production model based solely on the current small-sample results.



The benchmark provides a reproducible foundation for future model evaluation and evidence-based model selection.
